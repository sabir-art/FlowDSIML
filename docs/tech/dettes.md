# Dettes techniques

Points connus, acceptés pour l'instant, avec leur remède prévu.

| Date | Sujet | Constat | Impact | Remède prévu |
|---|---|---|---|---|
| 2026-11-18 | L11 : cache CDN des anciennes URL publiques | Depuis le passage du bucket « published » en privé (migration 20261118090000), le lecteur passe par l'Edge Function open-demo et des URL signées. Le Smart CDN de Supabase peut encore servir, depuis son cache, les objets demandés publiquement **avant** ce passage (par exemple `latest.json` de la démo fictive Nordline). | Faible : seules les démos publiées avant L11 et déjà consultées par leur URL publique sont concernées, et uniquement tant que le cache n'est pas renouvelé. Une démo passée ensuite en mot de passe ou avec expiration pourrait rester lisible par son ancienne URL publique en cache. | Si une démo réelle est concernée : réécrire ses fichiers publiés (upsert à l'identique, avec le service role), ce qui devrait invalider le cache du Smart CDN, ou les republier sous un nouveau préfixe. Aucun script tant que seule Nordline (fictive, en mode lien) est concernée. |
| 2026-11-18 | L11 : en-tête IP fiable pour open-demo | L'Edge Function prend `cf-connecting-ip`, sinon `x-real-ip`, sinon la dernière valeur de `x-forwarded-for`. L'en-tête réellement fourni par l'Edge Runtime n'est pas encore confirmé. Une trace par instance (`openDemoIpHeaders`, présence des en-têtes seulement, jamais de valeur) est en place pour le vérifier dans les logs. | Faible : le plafond global par démo (50 échecs en 1 h, puis 15 minutes de blocage) limite les essais même si l'IP pouvait être falsifiée. | Lire la trace depuis le tableau de bord Supabase, garder l'en-tête confirmé, puis retirer la trace. |
| 2026-11-18 | L23 : notification des admins à la pause automatique d'un webhook | La spec A5 §2 prévoit une notification aux admins quand un webhook passe en pause après 6 échecs. La table `notifications` (L22) ne porte que des références de commentaires. La pause est visible dans l'écran des webhooks (état « en pause automatique », journal). | Faible : l'admin voit la pause en ouvrant l'écran, mais n'est pas prévenu. | Corrigé (L29) : migration `20261123160000_webhook_pause_notif.sql`, notification « webhook en pause » aux propriétaires et admins (hôte seul), lien vers Intégrations ; test pgTAP `webhook_pause.test.sql`. |
| 2026-11-18 | L23 : fenêtre de rebinding DNS entre contrôle et envoi | L'Edge Function résout le nom et refuse toute IP privée, puis `fetch` refait sa propre résolution : un serveur DNS hostile pourrait répondre autre chose entre les deux (TTL très court). | Faible : redirections non suivies, délai de 10 s, réponse tronquée à 2 Ko, aucun en-tête d'authentification interne envoyé ; l'Edge Runtime n'expose pas de services internes du projet. | Épingler l'IP contrôlée pour la connexion (client HTTP avec résolution fixée) dès que l'Edge Runtime le permet. |
| 2026-11-19 | L25 : purge des vidéos orphelines en attente des secrets Vault | `videos_purge_tick` (pg_cron, chaque heure) appelle `webhooks-dispatch` avec les secrets Vault `webhooks_dispatch_url` et `webhooks_dispatch_secret`. Ces secrets ne sont pas encore créés (création reportée par le client) : le tick ne fait rien, sans erreur, comme celui des webhooks. | Moyen : les vidéos jamais rattachées à une étape (envoi interrompu, étape refusée) restent dans le bucket `videos` et comptent dans le quota de 500 Mo du workspace. | Créer les deux secrets dans Vault (et `WEBHOOKS_DISPATCH_SECRET` côté fonction) : la purge démarre seule au tick suivant. En attendant, suppression manuelle possible par l'API Storage à partir de `orphan_videos()`. |
| 2026-11-19 | L27 123 : exports générés dans le navigateur | La règle « Téléchargement des exports » est vérifiée par la base pour ce qui passe par elle : l'enregistrement d'une diffusion SCORM est refusé (`RULE_EXPORTS`). Les fichiers d'export (PDF, MP4, HTML, paquet SCORM) sont produits dans le navigateur à partir de données que le membre lit déjà : l'interface désactive ces exports dans l'app (menus « Exporter », « Générer le paquet »), mais un membre qui contourne l'interface peut encore produire un fichier. | Moyen : la règle limite les exports ordinaires ; elle ne protège pas d'un membre qui détourne volontairement le client. | Générer les exports côté serveur (Edge Function avec vérification des règles) si un client exige une garantie stricte. |
| 2026-11-19 | L27 : `set_demo_access` en mode mot de passe | Avant le correctif de la migration 20261122090000, régler l'accès d'une démo déjà protégée (par exemple changer son expiration) échouait sur la contrainte `demo_access_check` : la ligne proposée par `insert … on conflict` n'avait pas de mot de passe. | Corrigé : la fonction met à jour la ligne existante et n'insère que si elle n'existe pas (test pgTAP dans `regles_partage.test.sql`). | Aucun. |
| 2026-11-19 | L27-09 : images des démos d'un dossier restreint | Le filtrage par dossier porte sur les tables et les RPC. La politique du bucket `captures` reste celle de l'espace (membre de l'espace). | Moyen (revu en L29) : le listage de l'API de stockage applique la politique de lecture ; un membre exclu du dossier peut lister `<espace>/` et obtenir les identifiants des démos, puis leurs fichiers (voir docs/tech/securite-revue.md, S1). | Corrigé (L29, schéma E) : migration `20261123170000_stockage_dossiers.sql`, `demo_visible` ajouté aux politiques de `captures`, `videos`, `voices`, `html` et `published` ; test pgTAP `stockage_dossiers.test.sql` (chemin mal formé : rien au-delà de `has_role`). |
