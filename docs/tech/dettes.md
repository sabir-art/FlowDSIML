# Dettes techniques

Points connus, acceptés pour l'instant, avec leur remède prévu. Une dette réglée est barrée, avec sa date.

État au 2026-11-21 : 6 dettes réglées, 3 ouvertes. Les 3 ouvertes attendent une décision ou un accès
du client :

- en-tête IP fiable pour open-demo : lecture des journaux de production ;
- aperçu Open Graph : domaine personnalisé ;
- exports générés dans le navigateur : génération côté serveur, seulement si un client exige une garantie
  stricte.

| Date | Sujet | Constat | Impact | Remède prévu |
|---|---|---|---|---|
| 2026-11-18 | ~~L11 : cache CDN des anciennes URL publiques~~ **Réglée le 2026-11-20 (L37)** | Depuis le passage du bucket « published » en privé (migration 20261118090000), le lecteur passe par l'Edge Function open-demo et des URL signées. Le Smart CDN de Supabase peut encore servir, depuis son cache, les objets demandés publiquement **avant** ce passage (par exemple `latest.json` de la démo fictive Nordline). | Faible : seules les démos publiées avant L11 et déjà consultées par leur URL publique sont concernées, et uniquement tant que le cache n'est pas renouvelé. Une démo passée ensuite en mot de passe ou avec expiration pourrait rester lisible par son ancienne URL publique en cache. | Réglée (L37) : `scripts/refresh-published-cache.mjs` réécrit à l'identique les fichiers du bucket `published` antérieurs à la migration L11, ce qui invalide le Smart CDN (liste par défaut, `--apply` pour écrire ; clé service role passée dans l'environnement, jamais dans le dépôt). Test : `scripts/refresh-published-cache.test.mjs`, en CI. Reste une action d'exploitation : lancer le script une fois en production. Plus de nouvelle exposition possible : le bucket est privé et le lecteur n'utilise que des URL signées. |
| 2026-11-18 | L11 : en-tête IP fiable pour open-demo | L'Edge Function prend `cf-connecting-ip`, sinon `x-real-ip`, sinon la dernière valeur de `x-forwarded-for`. L'en-tête réellement fourni par l'Edge Runtime n'est pas encore confirmé. Une trace par instance (`openDemoIpHeaders`, présence des en-têtes seulement, jamais de valeur) est en place pour le vérifier dans les logs. | Faible : le plafond global par démo (50 échecs en 1 h, puis 15 minutes de blocage) limite les essais même si l'IP pouvait être falsifiée. | Lire la trace depuis le tableau de bord Supabase, garder l'en-tête confirmé, puis retirer la trace. |
| 2026-11-18 | ~~L23 : notification des admins à la pause automatique d'un webhook~~ **Réglée le 2026-11-20 (L29)** | La spec A5 §2 prévoit une notification aux admins quand un webhook passe en pause après 6 échecs. La table `notifications` (L22) ne porte que des références de commentaires. La pause est visible dans l'écran des webhooks (état « en pause automatique », journal). | Faible : l'admin voit la pause en ouvrant l'écran, mais n'est pas prévenu. | Corrigé (L29) : migration `20261123160000_webhook_pause_notif.sql`, notification « webhook en pause » aux propriétaires et admins (hôte seul), lien vers Intégrations ; test pgTAP `webhook_pause.test.sql`. |
| 2026-11-18 | ~~L23 : fenêtre de rebinding DNS entre contrôle et envoi~~ **Réglée le 2026-11-20 (L37)** | L'Edge Function résout le nom et refuse toute IP privée, puis `fetch` refait sa propre résolution : un serveur DNS hostile pourrait répondre autre chose entre les deux (TTL très court). | Faible : redirections non suivies, délai de 10 s, réponse tronquée à 2 Ko, aucun en-tête d'authentification interne envoyé ; l'Edge Runtime n'expose pas de services internes du projet. | Réglée (L37) : `webhooks-dispatch/pinned.ts` ouvre la connexion TCP vers l'IP contrôlée, puis négocie et vérifie TLS pour le nom d'hôte de l'URL (`Deno.startTls`) ; le nom n'est plus résolu une seconde fois. Le délai de 10 s couvre aussi la connexion TCP et la négociation TLS ; une connexion aboutie après l'abandon est fermée aussitôt. Tests : `pinned.test.ts` (IP utilisée, requête, réponse bornée, redirection, délai pendant la connexion et pendant l'échange) et `lib.test.ts` (une seule résolution). |
| 2026-11-19 | ~~L25 : purge des vidéos orphelines en attente des secrets Vault~~ **Réglée le 2026-11-21** | `videos_purge_tick` (pg_cron, chaque heure) appelle `webhooks-dispatch` avec les secrets Vault `webhooks_dispatch_url` et `webhooks_dispatch_secret`. Ces secrets ne sont pas encore créés (création reportée par le client) : le tick ne fait rien, sans erreur, comme celui des webhooks. | Moyen : les vidéos jamais rattachées à une étape (envoi interrompu, étape refusée) restent dans le bucket `videos` et comptent dans le quota de 500 Mo du workspace. | Réglée le 2026-11-21 : le chef a créé en production les secrets Vault `webhooks_dispatch_url` et `webhooks_dispatch_secret`, ainsi que `WEBHOOKS_DISPATCH_SECRET` côté fonctions. La purge, les webhooks et les résumés par e-mail (`email_digest_tick`, qui appelle notify-email avec le même secret) partent au tick suivant. Il ne manque que `BREVO_API_KEY` pour les résumés. |
| 2026-11-19 | L27 123 : exports générés dans le navigateur | La règle « Téléchargement des exports » est vérifiée par la base pour ce qui passe par elle : l'enregistrement d'une diffusion SCORM est refusé (`RULE_EXPORTS`). Les fichiers d'export (PDF, MP4, HTML, paquet SCORM) sont produits dans le navigateur à partir de données que le membre lit déjà : l'interface désactive ces exports dans l'app (menus « Exporter », « Générer le paquet »), mais un membre qui contourne l'interface peut encore produire un fichier. | Moyen : la règle limite les exports ordinaires ; elle ne protège pas d'un membre qui détourne volontairement le client. | Générer les exports côté serveur (Edge Function avec vérification des règles) si un client exige une garantie stricte. |
| 2026-11-19 | ~~L27 : `set_demo_access` en mode mot de passe~~ **Réglée le 2026-11-19 (L27)** | Avant le correctif de la migration 20261122090000, régler l'accès d'une démo déjà protégée (par exemple changer son expiration) échouait sur la contrainte `demo_access_check` : la ligne proposée par `insert … on conflict` n'avait pas de mot de passe. | Corrigé : la fonction met à jour la ligne existante et n'insère que si elle n'existe pas (test pgTAP dans `regles_partage.test.sql`). | Aucun. |
| 2026-11-19 | ~~L27-09 : images des démos d'un dossier restreint~~ **Réglée le 2026-11-20 (L29)** | Le filtrage par dossier porte sur les tables et les RPC. La politique du bucket `captures` reste celle de l'espace (membre de l'espace). | Moyen (revu en L29) : le listage de l'API de stockage applique la politique de lecture ; un membre exclu du dossier peut lister `<espace>/` et obtenir les identifiants des démos, puis leurs fichiers (voir docs/tech/securite-revue.md, S1). | Corrigé (L29, schéma E) : migration `20261123170000_stockage_dossiers.sql`, `demo_visible` ajouté aux politiques de `captures`, `videos`, `voices`, `html` et `published` ; test pgTAP `stockage_dossiers.test.sql` (chemin mal formé : rien au-delà de `has_role`). |
| 2026-11-20 | L34 : aperçu Open Graph | Aperçu Open Graph : attend un domaine personnalisé (décision client). Supabase sert en texte brut toute page HTML d'une Edge Function sur le domaine par défaut, et le fragment `#/p/…`, `#/l/…` n'est jamais envoyé au serveur. | Faible : un lien partagé s'affiche sans titre ni image dans les messageries et réseaux. | Avec un domaine personnalisé : Edge Function publique (mêmes règles que `resolve_share_link`, plafond de débit, image signée courte) et adresse de partage dédiée. |
